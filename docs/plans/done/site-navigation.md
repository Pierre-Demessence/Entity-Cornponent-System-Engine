# Site navigation: per-section sidebars, section landing pages, header links

## Requirements

- THE SYSTEM SHALL present a different left sidebar in the Manual and in the API
  reference, rather than one list covering both sections.
- THE Manual sidebar SHALL open with an **Overview** page and then a collapsed
  **Modules** group containing the 42 module guides.
- THE API sidebar SHALL open with the **Overview** page and then two collapsed
  groups, **Core API** and **Modules API**.
- THE home page SHALL present the Manual and API blocks as links, and SHALL NOT
  show the two hero action buttons above them.
- THE header SHALL offer a way into both sections.

## What the framework actually supports (verified, not assumed)

- **One sidebar is configured globally.** `starlight.sidebar` is a single
  `SidebarItem[]` (`starlight.astro.build/reference/configuration/#sidebar`);
  groups support `collapsed`, and autogenerated subgroups support
  `autogenerate.collapsed`. There is no per-section sidebar option.
- **Route data is per page and is mutable.** `starlightRoute.sidebar` is
  `Array<SidebarLink | SidebarGroup>` for the page, and route middleware
  (`routeMiddleware: './src/site-route-data.ts'`, `defineRouteMiddleware((context) => …)`)
  may modify route data. Assigning a section-specific array there is the
  supported mechanism — no plugin, no component override.
- **The header has no free-form link list.** `social` renders icon links in the
  header (`Array<{ label, icon, href }>`); anything else needs a component
  override. Two icons keep this dependency-free.
- **The generated API group is a single resolved tree.** `typeDocSidebarGroup` is
  swapped for one group holding every entry point, naming module pages after
  their path (`modules/spatial`). Splitting it into Core API and Modules API is
  therefore a *reorganisation of resolved entries*, which is exactly what route
  middleware is documented for — no second renderer instance, no second TypeDoc
  run, and no risk of two instances writing the same output directory.

## Design

### 1. The configured sidebar stays the superset

`astro.config.mjs` keeps both top-level groups exactly as they were — `Manual`
(autogenerated from `manual/`) and `API reference` (holding the plugin's
`typeDocSidebarGroup`, which the plugin replaces by label). Starlight resolves
that config per page: expanding `autogenerate`, computing every `href`, marking
the current page. The middleware then only *rearranges* the resolved entries, so
link generation, ordering and highlighting are never reimplemented.

### 2. Per-section selection in route middleware

`website/src/site-route-data.ts` decides the section from the URL path relative
to `import.meta.env.BASE_URL` (not from the page id, so `/manual/` — the section
root — classifies correctly too):

- `/manual/**` → `Overview` link + a collapsed `Modules` group holding the
  resolved guide entries.
- `/api/**` → `Overview` link + collapsed `Core API` + collapsed `Modules API`,
  where the generated group's entries are split on TypeDoc's `modules/` label
  prefix, which is also stripped, so a heading reads `animation` rather than
  `modules/animation`.
- anything else (the splash home page, the 404) is left untouched.

Two typing details cost a round of `tsc` each: resolved entries require
`badge: Badge | undefined` explicitly, and `Array.find` needs an inline type
predicate to narrow to a group.

### 3. Manual Overview = a curated page

The repository README is written for repo visitors (badges, `file:` install,
`0.0.0` disclaimers), so `/manual/` gets a **curated** Overview instead: the
prose is authored in `website/manual-overview.md` — the one site source outside
the generator — and `scripts/manual.ts` adds the frontmatter (title `Overview`,
description from its first paragraph) and the `sidebar: hidden` flag before
writing `manual/index.md`.

Keeping the prose in a committed file and the frontmatter in the generator means
everything under `website/src/content/docs/manual/` stays generated, so the
never-hand-place-anything-there invariant holds and the build keeps
`rmSync`-ing that directory.

### 4. API split: core vs modules

No second renderer instance: every generated group is partitioned in the
middleware (the shipped config contributes exactly one). Entries whose label
starts with TypeDoc's `modules/` prefix (from the `./src/modules/*/index.ts`
entry glob) go under **Modules API**, everything else under **Core API**, and the
prefix is stripped so a heading reads `animation`.

Rejected alternative, recorded so it is not re-attempted — two plugin instances:

```js
const [coreTypeDocPlugin, coreTypeDocGroup] = createStarlightTypeDocPlugin()
const [modulesTypeDocPlugin, modulesTypeDocGroup] = createStarlightTypeDocPlugin()

plugins: [
  coreTypeDocPlugin({
    entryPoints: coreEntryPoints(),
    output: 'api',
    sidebar: { label: 'Core API' },
    tsconfig: './tsconfig.json',
    typeDoc: { excludeInternal: true, readme: 'none' },
  }),
  modulesTypeDocPlugin({
    entryPoints: ['./src/modules/*/index.ts'],
    output: 'api/modules',
    sidebar: { label: 'Modules API' },
    tsconfig: './tsconfig.json',
    typeDoc: { excludeInternal: true, readme: 'none' },
  }),
]
```

URLs are untouched: the split only moves entries between sidebar groups (`/api/<entry>/<kind>/<symbol>/` for core, `/api/modules/<name>/…` for a module).

That path doubles the TypeDoc run and puts two writers on one output directory,
for a split that is a sidebar concern rather than a rendering one.

### 5. Home page and header

- `website/src/content/docs/index.mdx`: make the two section blocks link to
  their sections and delete `hero.actions` (the tagline stays). They are
  Starlight `Card`s — which accept an `icon` — wrapped in an anchor, not
  `LinkCard`s, because `LinkCard` has no `icon` prop and would silently drop
  them. `website/src/styles/custom.css` carries the hover state and re-derives
  the card colour cycle from the wrapper.
- `astro.config.mjs`: add two `social` entries with base-prefixed hrefs.

## Verification

- Manual and API pages expose **different** sidebar entry sets (compare the
  built `website/dist/manual/*/index.html` and `website/dist/api/**/index.html`
  sidebar regions; assert the Manual sidebar has no `/api/` links and vice
  versa).
- The Manual sidebar shows exactly `Overview` + a collapsed `Modules` group of
  42 entries; the API sidebar shows exactly `Overview` + `Core API` +
  `Modules API`.
- Home page: no hero buttons; both blocks are link cards whose anchors resolve to
  `/manual/` and `/api/`.
- Page count and route inventory unchanged apart from intended changes; no new
  leaked `docs/**` links.
- Gates: `npm run lint`, `npm run typecheck`, `npm test`, `npm run docs:site`.
